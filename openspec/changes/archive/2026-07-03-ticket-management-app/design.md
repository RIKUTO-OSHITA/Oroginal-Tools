## Context

現在このリポジトリは空(OpenSpec構成のみ)であり、フロントエンド/バックエンドの技術スタックは未選定。proposal.mdで定義した5つのcapability(`ticket-crud`, `ticket-permalink`, `ticket-board`, `completed-tickets-archive`, `ticket-persistence`)を実現するための技術方式をここで決定する。

ユーザーからの制約:
- サーバー運用の手間を増やしたくない小規模ツールであること
- 各チケットに `Tickets-N` 形式の連番IDを付与すること
- チケットごとに固有URLを発行すること
- チケットは追加後、アプリを閉じても保持され続けること

## Goals / Non-Goals

**Goals:**
- ブラウザだけで完結し、サーバー構築・運用不要でチケット管理ができるSPAを構築する
- チケットごとに `Tickets-N` の連番IDと、そのIDに基づく固有URLを発行する
- チケットデータをブラウザの永続ストレージに保存し、再読み込み・再起動後も保持する
- Jira風のステータス別ボード表示と、完了チケット専用ページを提供する

**Non-Goals:**
- 複数ユーザー間でのリアルタイム共有・同時編集(1ブラウザ=1ユーザー前提)
- 複数デバイス/複数ブラウザ間でのデータ同期(将来的にバックエンドAPIへ移行する余地は残すが、本変更のスコープ外)
- 認証・権限管理
- ドラッグ&ドロップでのステータス変更、検索/フィルタ、削除の取り消し(ソフトデリート)は本変更では扱わない

## Decisions

### 1. フロントエンド構成: React + TypeScript + Vite
理由: 軽量なSPAを素早く構築でき、コンポーネント単位でボード/詳細/完了ページを分割しやすい。TypeScriptにより、チケットのフィールド(名前・目的・受け入れ条件・補足・ステータス・ID)を型として明示し、フォームやストレージ層のバグを防ぐ。
代替案: Vue、Svelte も検討したが、エコシステムとルーティングライブラリの成熟度からReactを採用。

### 2. ルーティング: React Router (HashRouter)
`ticket-permalink` 要件(チケットごとの固有URL、リロードしても同じ画面が表示される)を満たすためReact Routerを採用する。`BrowserRouter`ではなく`HashRouter`を選ぶ理由は、サーバー側のフォールバック設定(全パスをindex.htmlに向ける設定)が不要で、静的ファイルをそのまま配信するだけで動作するため。URL形式は `#/tickets/Tickets-1` のようになる。
代替案: `BrowserRouter`はURLが綺麗(`/tickets/Tickets-1`)だが、静的ホスティング環境によっては直接アクセス・リロード時に404になる設定が必要。本ツールの運用負荷を下げるためHashRouterを優先。

### 3. データ永続化: ブラウザ `localStorage`
`ticket-persistence`要件(アプリを閉じても保持される)を満たすため、バックエンドDBの代わりに`localStorage`にチケット一覧とID採番カウンタをJSONとして保存する。ストレージアクセスは`ticketStore`のような単一のリポジトリ層に閉じ込め、将来バックエンドAPIに差し替えられるようインターフェースを分離する。
代替案: バックエンドAPI+DB(例: Express+SQLite)も検討したが、サーバー運用が必要になりGoals(サーバー不要)に反するため見送り。将来複数デバイス間共有が必要になった場合の拡張ポイントとしてOpen Questionsに記載する。

### 4. チケットID採番方式: 単調増加カウンタ
`Tickets-N`のNは、これまでに作成された最大の番号+1として払い出す。削除してもカウンタは戻さない(ID再利用をしない)。カウンタ自体もlocalStorageに保存し、チケット配列とは独立して管理する。
理由: チケット削除後に新規作成したチケットが既存(または過去に削除済み)のIDと衝突する事故を防ぐため。

### 5. 状態管理: React Context + カスタムフック
Redux等の外部状態管理ライブラリは導入せず、`TicketsProvider`(Context)がlocalStorageとの同期を担い、`useTickets()`フックを通じて各ページ/コンポーネントがCRUD操作を呼び出す。
理由: チケット管理という単一ドメインの小規模アプリにおいて、Reduxなどの導入は過剰。Context+フックで十分にテスト可能かつシンプル。

### 6. ボード/完了ページの分割方針
ステータスは `todo` / `in_progress` / `done` の3種類。`/`(ボード)では`todo`と`in_progress`のチケットのみを列表示し、`done`になったチケットは自動的にボードから消え、`/completed`ページ一覧に表示される。

## Risks / Trade-offs

- [Risk] `localStorage`はブラウザ/デバイスごとに独立しているため、別のPCやブラウザからは同じチケットが見えない → [Mitigation] proposalの永続化要件は満たすが既知の制約としてREADME等に明記し、将来バックエンド化する際の抽象化(ストレージ層の分離)を今のうちに用意しておく。
- [Risk] ブラウザの「閲覧データ削除」やプライベートブラウジングモードでは`localStorage`が消去/利用不可になり、チケットが失われる可能性がある → [Mitigation] 既知の制約として明記。将来的にJSONエクスポート/インポート機能を追加する余地をOpen Questionsに残す。
- [Risk] `HashRouter`のURL(`#/tickets/Tickets-1`)は`BrowserRouter`より見た目が冗長 → [Mitigation] サーバー設定不要という運用上のメリットを優先。将来サーバーホスティングに移行する際に`BrowserRouter`へ切り替え可能な設計とする。

## Migration Plan

新規構築のため既存データの移行は不要。初期セットアップの流れ:
1. Vite + React + TypeScriptでプロジェクトを scaffold する
2. `ticketStore`(localStorageラッパー)を実装し、CRUD・ID採番ロジックを実装する
3. `TicketsProvider`/`useTickets`フックを実装する
4. ルーティング(`/`, `/tickets/new`, `/tickets/:ticketId`, `/completed`)を実装する
5. ボード画面・詳細/編集画面・完了一覧画面のUIを実装する
6. 手動での動作確認(作成・編集・削除・URL直接アクセス・リロード後のデータ保持)を行う

ロールバック戦略: 本変更はリポジトリ初期構築のため、問題があれば当該コミット/ブランチを破棄すればよく、既存システムへの影響はない。

- チケットデータのエクスポート/インポート(JSONバックアップ)機能を今後追加するか
